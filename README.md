# Resume Tailor — 把一份简历变成「针对这个 JD 的版本」

Resume Tailor 不是一个把简历润色得更顺的 AI 工具，而是一条**可检查、可拒绝、可回滚的 JD 定制工作流**：

> 先判断这个岗位到底在招什么人，再决定这份简历该不该投；值得投时，只把真实经历重新组织成更匹配的版本。

它最重要的设计选择是：**简历优先以 HTML 保存，PDF 作为兼容入口。**

这不是为了多支持一种文件格式，而是因为简历定制的核心动作是「对已有内容做精确修改」。PDF 适合阅读和投递，却不适合可靠地修改；HTML 既能保留用户原来的排版，又能让每一条被确认的修改真正落到原文上。

## 为什么输入 HTML，尤其是为什么 HTML 是主格式

### PDF 是交付格式，不是编辑格式

PDF 把排版固定下来，却把内容和版式绑定在了页面坐标上。对一份 PDF 做「把这一条经历换个动词、把这个项目提前、删掉这一段」时，通常要面对：

- 文本可能按字形、文本片段或双栏坐标拆散，阅读顺序不可靠；
- 修改一句话可能导致换行、分页、字体和间距连锁变化；
- 很难把一次修改稳定地定位到「第几段经历的第几个 bullet」；
- AI 直接重写整份 PDF，容易破坏原有信息和版式，也很难逐条确认。

因此 PDF 在 Resume Tailor 中承担的是**导入和兼容**：先用 pdf.js 按页面坐标重建文本，再让模型把文本解析成结构化简历；解析结果会经过用户核对，拿不准的字段标记为「待确认」，而不是悄悄当成事实。

### HTML 是可编辑的简历源文件

HTML 的优势不只是「容易读」，而是它把简历变成了可以被程序安全操作的文档：

1. **内容与样式分离**：原有 CSS、颜色、间距、双栏结构和模板都可以继续使用，定制时主要改文字，而不是重新排版。
2. **能做文本节点级定位**：系统会在可见文本节点中寻找 AI 给出的 `oldText`，先尝试单节点精确匹配，再支持跨连续节点匹配，最后才做空白归一化匹配。
3. **每条修改都有确定结果**：命中才替换；找不到就标记为 skipped，不做模糊猜测，不因为一次匹配失败而破坏整份简历。
4. **修改粒度足够小**：可以只替换一个 bullet、一个动词或一个技能词，而不是让模型重新生成全文。
5. **结果仍然是 HTML**：应用后可以立即预览、下载、继续编辑，也可以直接用浏览器打印为 PDF。

换句话说，HTML 让「AI 建议」变成了**可验证的补丁（patch）**，而不是一份需要用户重新校对的 AI 新稿。

### 两条输入链路，共享同一套定制逻辑

| 输入 | 处理方式 | 适合什么场景 | 代价 / 限制 |
|---|---|---|---|
| **HTML（主链路）** | 原文直接分析；修改时定位可见文本节点并返回新 HTML | 已有可编辑模板、重视原版式、需要频繁定制多个岗位 | 需要先有 HTML 模板；跨标签替换时，替换区间内的内联样式会并入纯文本 |
| **PDF（兼容链路）** | pdf.js 坐标分行 → 结构化解析 → 用户核对 → 按 section/index 修改 → 重新渲染 | 手头只有招聘网站导出的 PDF，想快速导入既有简历 | 这是一次结构化重建，不承诺保留原 PDF 的精确视觉版式；扫描件没有可提取文本时无法自动解析 |

PDF 不是被排除在外，而是被放在正确的位置：**PDF 用来带着旧简历进入系统，HTML 用来持续迭代，最终再生成投递文件。**

## 它解决什么问题

海投时代，一份通用简历打所有岗位是最低效的做法；但手动为每个 JD 定制又太贵。Resume Tailor 把「定制」变成一条可确认的流水线：

1. **贴 JD、选 base 简历**
2. **翻译岗位** — 识别职位族、级别、工作性质、团队位置、协作对象和误读风险；把职责拆成建设 / 探索 / 维护三类，并还原典型工作日
3. **判断是否值得投** — A/B/C/D 定性分档；硬门槛逐条判断 met / partial / gap，并引用简历或素材中的证据
4. **生成修改策略** — 措辞微调、换主线或大改重构；结构动作（删无关、扶正真实素材）与措辞动作分开
5. **逐条确认 diff** — 每条修改可编辑、勾选或拒绝，也可以要求 AI 只重写这一条
6. **应用并验证** — 查看应用 / 跳过结果，检查核心关键词覆盖，预览并保存为新版本
7. **投后闭环** — 记录投递状态，并按一面、二面或 HR 轮次生成项目下钻卡、gap 防御卡和反问清单

## 真正的产品亮点

### 1. 不是关键词润色，而是先还原岗位

JD 五层解构让模型先回答「这个岗位实际在做什么」，再回答「我的简历该怎么改」：

- 岗位定性：职位族、细分方向、级别、主要产出物
- 团队画像：组织位置、服务对象、岗位存在的原因、误读风险
- 职责翻译：行业术语的白话解释，以及建设 / 探索 / 维护的任务结构
- 筛选逻辑：机器硬筛规则、要求排序透露的团队痛点、团队气质
- 验证假设：把推断转成面试时可以向面试官求证的问题

### 2. 差距越大，不一定是多写关键词，而可能是换主线

系统明确区分三种修改幅度：

- **措辞微调**：方向基本对口，只调整动词、顺序和关键词
- **换主线**：方向相近，但需要把另一段真实经历扶正
- **大改重构**：删除无关经历，重新组织内容结构

素材库和隐藏经历池用于补充用户真实但尚未写入简历的经历；系统只使用用户提供的事实，不凭空编造项目和数字。

### 3. AI 提建议，人决定什么进入最终简历

编辑方案不是一次性生成全文，而是结构化的逐条 diff：

- 每条修改保留原文锚点、修改后文本和修改理由；
- 用户可以改文字、取消某条，或提出自然语言要求重新生成；
- 应用前后都会返回 applied / skipped 结果；
- HTML 链路找不到原文时宁可跳过，也不做模糊替换；
- 可以保存为新的「公司版本」，不覆盖 base 简历。

### 4. 不是生成完简历就结束

投递看板记录每个 JD、所用简历版本、当前轮次和时间线。进入面试后，针对下一轮生成：

- 项目下钻：结果、过程、反思三层
- 高频追问及接法
- gap 的诚实承认、可迁移证据和学习行动
- 60 秒自我介绍主线
- 反问清单与面试前检查项

## 数据和模型边界

- 简历、素材卡、隐藏经历池、投递记录和模型设置保存在浏览器 IndexedDB；服务端不使用数据库。
- 服务端只负责调用用户配置的 OpenAI 兼容模型服务并返回结构化结果；使用外部模型时，简历内容仍会发送到该模型服务，请按自己的隐私要求选择服务商。
- LLM 负责岗位理解、证据判定和修改建议；匹配度使用 A/B/C/D 定性档，不伪造一个看似精确的数字分数。
- Zod schema 约束分析、编辑计划和结构化简历结果；支持 `json_schema` 的模型使用 strict 输出，不支持时自动降级到 `json_object`，解析失败会自动重试一次。

## 快速开始

```bash
git clone <repo-url> && cd resume-tailor
npm install
npm run start          # http://localhost:3000
```

在「设置」页填一个 OpenAI 兼容的模型服务即可开始（API 地址 / 模型名 / Key 保存在浏览器本地）：

- **DeepSeek**：`https://api.deepseek.com/v1` + `deepseek-chat`
- **通义千问**：`https://dashscope.aliyuncs.com/compatible-mode/v1` + `qwen-plus`
- **OpenAI / 其他兼容网关**：填 base URL 和模型名即可

建议的使用方式：

1. 先准备一份带 CSS 的 HTML 简历作为长期维护的 base；
2. 只有 PDF 时先导入，核对结构化结果后保存；
3. 每个 JD 生成一个派生版本，不覆盖原始简历；
4. 应用后查看跳过项和关键词覆盖，再下载 HTML 或打印为 PDF 投递。

## 架构

```
public/                 前端（原生 JS 单页应用，零构建）
  index.html            页面结构与分步向导骨架
  app.js                IndexedDB、文件导入、PDF 解析、diff、预览与交互
  style.css             全部样式
src/
  server.ts             Express / Vercel API 端点
  analyze.ts            LLM 结构化输出、HTML / PDF 两条分析与编辑链路
  prompts.ts            JD 解构、筛选、编辑策略、简历解析、面试 prep prompts
  apply.ts              HTML 文本节点级定位、确定性替换与关键词覆盖
  structuredApply.ts    PDF 解析后的结构化简历按 section / index 修改
api/index.ts            Vercel 函数入口
```

### HTML 链路

```text
HTML 文件
  → 浏览器读取并存入 IndexedDB
  → LLM 分析可见内容
  → 生成 oldText / newText 编辑指令
  → Cheerio 定位文本节点并确定性替换
  → 返回 applied / skipped 结果与关键词覆盖
  → 预览、另存为新版本、下载 HTML / 浏览器打印 PDF
```

### PDF 链路

```text
PDF 文件
  → pdf.js 提取文本
  → 按 y 坐标重建行、按 x 坐标排序（兼顾双栏）
  → LLM 解析为结构化简历
  → 用户核对并补填低置信度字段
  → 按经历 / 项目 / bullet 下标生成修改
  → 结构化应用、预览并导出
```

## 部署

Vercel（Hobby 计划可直接部署，`vercel.json` 已配置）：

```bash
npx vercel
```

注意 Hobby 计划函数约 55 秒超时上限：完整分析在慢模型上可能超时，重试或换更快的模型即可。PDF 解析和 PDF 导入 / 导出依赖浏览器按需加载的 pdf.js / pdf-lib；离线或 CDN 不可用时，HTML 链路仍是更可靠的选择。
