# Resume Tailor — 先读懂 JD，再定制简历

Resume Tailor 不是一个把简历润色得更顺的 AI 工具，而是一个帮助你回答两个问题的求职工作台：

1. **这个岗位实际上在做什么？**
2. **我的经历，应该怎样被组织成这个岗位想看到的样子？**

它把 JD 里常见的“大词、套话和模糊要求”，翻译成可理解、可验证、能直接指导投递的具体判断；再基于你的真实经历，给出是否值得投以及该如何修改简历的定制方案。

## 核心价值：把 JD 从“招聘话术”翻译成“真实工作”

很多 JD 写的是“负责业务增长”“推动跨部门协作”“深入理解行业”“参与全链路建设”，但求职者真正想知道的是：

- 入职后第一个月具体会做什么？
- 每天最常和谁沟通，交付给谁？
- 这个岗位产出的到底是代码、方案、分析报告，还是协调结果？
- JD 中哪些要求是机器筛选的硬门槛，哪些只是加分项？
- 团队现在最痛的是什么，为什么要招这个人？
- “熟悉”“深入理解”“有业务 sense”究竟要做到什么程度？

Resume Tailor 会从团队位置、业务价值链、职责排序和加分项反推岗位真实画像，输出：

- **岗位定性**：职位族、细分方向、级别和主要产出物
- **团队画像**：这个岗位挂在哪个团队、服务谁、为什么存在
- **交互画像**：高频协作对象是谁，沟通是研究型、协调型、执行型还是对外型
- **职责翻译**：把抽象职责还原成具体工作场景，并区分建设、探索、维护三类任务
- **典型工作日**：把 JD 还原成入职后的日常节奏
- **行话速成**：用白话解释岗位语境中真正重要的术语
- **筛选逻辑**：机器筛什么、HR 看什么、面试官会深挖什么
- **验证问题**：把判断和假设转成面试时可以向面试官求证的问题

如果 JD 本身信息很少，系统还会进入生成模式：从公司业务、商业模式和价值链推断这个岗位可能承担的实际任务，并明确哪些是待验证的假设，而不是把猜测伪装成事实。

## 从“读懂岗位”到“判断匹配”

读懂 JD 之后，Resume Tailor 不直接给你一个虚假的百分制分数，而是做一份有证据的匹配判断：

- **A｜值得投**：方向对口，核心经历直接命中
- **B｜改后投**：方向对口，但主线或关键词有缺口，修改后能补救
- **C｜观望**：方向相近，但需要换主线或依赖素材库里的迁移经历
- **D｜不建议投**：方向不符，或机器筛硬门槛无法通过

每个硬门槛和加分项都会标记为：

- `met`：简历已有直接证据
- `partial`：有相近经历，但当前简历没有明确写出来
- `gap`：简历和素材库都没有证据

这样你看到的不只是“匹配度”，还知道**为什么匹配、差在哪里、这个差距能不能靠改简历解决**。

## 定制的重点不是润色，而是重新组织证据

确认值得投之后，系统会根据岗位差距选择修改幅度：

- **措辞微调**：方向基本一致，只调整动词、顺序、重心和关键词
- **换主线**：方向相近，但更相关的经历没有被放在主角位置
- **大改重构**：删除无关内容，从真实素材中扶正另一条经历主线

定制动作不是单纯“多塞几个关键词”，而是：

> **删无关，改相关，补缺口。**

素材库和隐藏经历池用于保存那些真实存在、但没有放进当前简历的经历，例如课程项目、社团、班干部、兼职或被裁掉的成果。系统可以在合适的 JD 下把它们重新启用，但不会编造项目、数字或能力。

## AI 建议，人确认每一条修改

Resume Tailor 不一次性生成一份无法追溯的“新简历”，而是生成逐条 diff：

- 每条修改都有原文、改后文本和修改理由；
- 结构动作和措辞动作分开呈现；
- 用户可以编辑、勾选或拒绝任意一条；
- 不认同某条时，可以用自然语言要求 AI 只重写这一条；
- 应用后返回每条修改的 `applied` / `skipped` 结果；
- 核对核心关键词覆盖率，并预览最终版本；
- 可以保存为某个公司的派生版本，不覆盖 base 简历。

这让 AI 输出更像**可检查的修改补丁**，而不是需要重新校对全文的生成稿。

## HTML 与 PDF：简历源文件和投递文件分开

产品支持 HTML 和 PDF，但两者承担不同角色：

- **HTML 是更适合长期定制的源文件**：保留原有 CSS 和版式，系统可以直接定位可见文本节点，只替换具体 bullet、动词或技能词，修改后仍可预览、下载，或用浏览器打印成 PDF。
- **PDF 是兼容入口**：使用 pdf.js 提取文本，按坐标重建行，再由模型解析为结构化简历；用户核对后按经历和 bullet 修改。它适合手头只有 PDF 的情况，但不承诺保留原 PDF 的精确视觉版式，扫描件也可能无法提取文本。

简单说：**PDF 帮你把旧简历带进来，HTML 让你可以持续定制，最终再生成投递文件。**

## 一条完整工作流

1. 上传或选择 base 简历，粘贴目标 JD
2. 先看岗位解构：岗位实际做什么、和谁协作、典型一天如何度过
3. 查看 A/B/C/D 匹配结论、硬门槛、加分项和关键词缺口
4. 确认是否生成修改方案
5. 逐条确认 diff，必要时要求重写
6. 应用修改，检查跳过项和核心词覆盖率
7. 预览并保存针对该公司的简历版本
8. 记录投递状态，并按一面、二面或 HR 生成面试准备

投后还可以继续使用：投递看板记录 JD、简历版本和流程状态；面试准备包含项目下钻卡、结果 / 过程 / 反思、gap 防御、60 秒自我介绍、反问清单和面试前检查项。

## 数据边界

- 简历、素材、隐藏经历、投递记录和模型设置保存在浏览器 IndexedDB，服务端不使用数据库。
- 服务端主要负责调用用户配置的 OpenAI 兼容模型并返回结构化结果；使用外部模型时，简历内容会发送给对应模型服务，请按隐私要求选择服务商。
- LLM 负责岗位理解、证据判定和修改建议，不负责编造事实，也不使用看似精确但不可解释的数字评分。
- 分析、编辑计划和结构化简历均使用 Zod schema 约束输出，支持 `json_schema` 的模型使用 strict 模式，不支持时自动降级到 `json_object`。

## 快速开始

```bash
git clone <repo-url> && cd resume-tailor
npm install
npm run start          # http://localhost:3000
```

在「设置」页填一个 OpenAI 兼容的模型服务（API 地址 / 模型名 / Key）：

- **DeepSeek**：`https://api.deepseek.com/v1` + `deepseek-chat`
- **通义千问**：`https://dashscope.aliyuncs.com/compatible-mode/v1` + `qwen-plus`
- **OpenAI / 其他兼容网关**：填写 base URL 和模型名

## 架构

```
public/                 前端（原生 JS 单页应用，零构建）
  index.html            页面结构与分步向导
  app.js                IndexedDB、文件导入、PDF 解析、diff、预览与交互
  style.css             全部样式
src/
  server.ts             Express / Vercel API 端点
  analyze.ts            LLM 结构化输出与 HTML / PDF 两条链路
  prompts.ts            JD 解构、匹配判断、编辑策略、简历解析、面试 prep
  apply.ts              HTML 文本节点定位、确定性替换与关键词覆盖
  structuredApply.ts    PDF 解析后的结构化简历按 section / index 修改
api/index.ts            Vercel 函数入口
```

## 部署

Vercel（Hobby 计划可直接部署，`vercel.json` 已配置）：

```bash
npx vercel
```

注意 Hobby 计划函数约 55 秒超时上限：完整分析在慢模型上可能超时，重试或换更快的模型即可。PDF 解析依赖浏览器按需加载 pdf.js；离线或 CDN 不可用时，HTML 链路仍可使用。
